---
title: Extensions
description: One package, up to six attachment points — relay, headless, workspace, GUI, executables, background.
---

Think about what "the git extension" means in fez. Five different things,
actually: the *relay* serving repositories over HTTP, a */repo command*
you run yourself, a *provider* that turns a persona's `repo:` into a
checkout, a *panel and lane board* in the desktop, and a credential
helper on your `PATH`. fez's extension model embraces that: **one
package, several optional attachment points**, declared in the
package's `package.json`:

```json
"fez": {
  "parts": {
    "skill":      { "command": "npx", "args": ["-y", "some-mcp"], "env": { "API_KEY": "" } },
    "relay":      "dist/relay-part.js",
    "headless":   "dist/headless.js",
    "workspace":  "dist/workspace-part.js",
    "gui":        "dist/gui.js",
    "background": true
  },
  "bin": { "my-tool": "dist/tool.js" },
  "permissions": ["read:channels", "publish", "commands", "ui", "background", "personas"]
}
```

- **relay** — HTTP handlers, ingest policies, and NIP-11 advertisements,
  loaded only by a relay started with `--extensions`. The relay holds no
  signing key, so a relay part can *record and serve* but never speak.
- **headless** — commands and scheduled tasks that run beside the
  owner's key (TUI and sentinel) — the half that CAN speak on the relay.
- **workspace** — gives a `repo:` persona a working checkout.
- **gui** — panels, composer commands, and thread views in the desktop,
  each behind a permission the install dialog names (`personas` is the
  sensitive one: it is the power to reprogram agents).
- **bin** — npm's own `bin` map, honored: executables land in
  `~/.fez/bin`.
- **background** — opts the headless part's scheduled tasks into the
  always-on sentinel.

`@fezchat/git` exercises every one of them and is the worked example.

One `fez install` (or `fez link <dir>` for local dev) registers whatever parts
exist:

- **`skill`** — an MCP server definition, merged into the machine's skill
  catalog. Agents get it by declaring the name in their persona
  ([how skills work](/docs/concepts/skills)). This is the *"@deployer, upload
  the results"* path — no GUI involved.
- **`headless`** — code loaded by **any** client (TUI and GUI alike) against
  the `FezExtensionAPI`: slash commands, services, new event kinds. This is
  the */obsidian* path — and why the system still works with no GUI at all.
- **`gui`** — components only the desktop app renders. Loaded from
  `~/.fez/gui-extensions` at launch; `activate(api)` receives the page's React
  (there is exactly one React on the page) plus the seams it has permission
  for:

  | seam | what it claims |
  | --- | --- |
  | `registerArtifactViewer` | a typed artifact — how `artifact:html` renders |
  | `registerTheme` | a CSS-variable pack, listed in settings → appearance |
  | `registerMessageDecorator` | a card under matching chat messages (how polls appear) |
  | `registerGuiCommand` | a slash command in the composer |
  | `registerMarkdownPlugin` | markdown *parsing*, everywhere docs render |
  | `registerBlockRenderer` | one fenced block language (` ```fez:live ` ) |
  | `registerPageView` | a whole document, rendered another way |

  The last one is how [boards](/docs/concepts/docs) exist: an extension says
  "this document is a board" and gets to render it, with a `save` that
  publishes a new version and a `comment` that anchors a thread to a line.
  Markdown stays one click away, so a view is a lens on the document rather
  than a replacement for it.

- **`background`** — opt in to running scheduled work inside the always-on
  [sentinel](/docs/self-hosting). The extension registers tasks with
  `api.registerScheduledTask(name, everyMs, run)`; the sentinel is the only
  host that runs them, so no extension ships its own daemon. This is an
  allowlist, not a default: an extension written for the TUI would otherwise
  start doing its foreground job a second time inside the always-on process.

Alongside `parts`, a package declares **`permissions`** — what it needs, shown
to the user before anything runs, and enforced by narrowing the API it receives.
See [trust & approval](/docs/concepts/trust).


A package ships only the parts that make sense: a bitwarden package might be
`skill` + `headless` (no UI needed); a theme pack is `gui` only; an obsidian
package plausibly ships all three. The substance always lives in the first
two — `gui` is presentation.

## Installing

```bash
fez install <source>    # npm package, git URL, or local path
fez list                # what's installed
fez remove <name>       # uninstall (skill definitions are kept — see below)
fez link <dir>          # dev-install a local package: build, register parts, smoke-import
```

Removal keeps the skill *definition*: personas may still declare it, and any
secret values you filled are yours ([custody](/docs/concepts/skills#secrets)).

## The first-party packages

The features you'd assume are core are themselves extensions with no private
hooks — proof the seams are real: fez-communities (the channel UI itself),
fez-dms, fez-docs, fez-media (Blossom uploads), fez-moderation,
fez-notifications, fez-search, fez-workflows, theme packs.

## The rule

If a feature can live behind a seam, it must. Core grows only when a new
*seam* is needed — never a new feature.
