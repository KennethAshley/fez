fez's rule is simple: **if a feature can live behind a seam, it must.** Core
grows only when a new seam is needed — never a new feature. Extensions are how
everything user-facing ships, and this section is the contract you build them
against.

## The surface model

A fez extension is **one npm package** with up to six optional attachment
points, declared under the `fez` key in `package.json`. Each part is a single
bundled file that `fez install` copies into a well-known directory under
`~/.fez/`; the corresponding host discovers it, imports it, and calls the
default export with an injected API.

| Part | Installs to | Loaded by |
| --- | --- | --- |
| `headless` | `~/.fez/extensions/` | the TUI and the sentinel |
| `gui` | `~/.fez/gui-extensions/` | the desktop app's webview |
| `relay` | `~/.fez/relay-extensions/` | a relay started with `--extensions` |
| `workspace` | `~/.fez/workspace-providers/` | the agent runtime, for `repo:` personas |
| `skill` | `settings.json` → `mcpServers` | agents at spawn (an MCP server definition) |
| `background: true` | `settings.json` allowlist | opts your headless part into the always-on sentinel |

Plus npm's own `bin` map (→ `~/.fez/bin/`) and `fez.personas` for shipping
persona packs — [`@fezchat/score-studio`](/docs/reference/packages) is a
complete extension that ships *only* a persona.

One `fez install` places every part; each host picks up its own. Note that
headless parts load in the **TUI and sentinel only** — the desktop app loads
`gui` parts, not headless ones.

## The contract package

```sh
npm install -D @fezchat/extension-api
```

```ts
import type { FezExtensionAPI } from "@fezchat/extension-api/headless";
import type { GuiExtensionApi } from "@fezchat/extension-api/gui";
import type { RelayExtensionAPI } from "@fezchat/extension-api/relay";
import type { WorkspaceProvider } from "@fezchat/extension-api/workspace";
```

It is **types only** — every export erases at bundle time, so your shipped
part carries zero runtime dependency on fez. (Some first-party packages
instead carry a hand-written structural mirror in `src/api-types.ts`; a
conformance eval keeps every mirror honest against the host. For new
extensions, use the package.)

The published contract is a deliberate subset of what hosts implement; a few
host-only registration seams (harnesses, themes, system-prompt sections) are
noted on each surface's page.

## Which surface do I need?

- A slash command or a scheduled job → **[headless](/docs/extension-api/headless)**
- A card under messages, a panel, a view over a doc → **[gui](/docs/extension-api/gui)**
- Serving HTTP from the relay (git, media) → **[relay](/docs/extension-api/relay-workspace)**
- Giving a `repo:` persona its checkout → **[workspace](/docs/extension-api/relay-workspace)**
- A tool agents call → the **`skill`** part (an MCP server your package ships
  — see [the manifest](/docs/extension-api/manifest))

Worked examples in the repo: `packages/fez-polls` (headless + gui + skill
sharing one vote-logic module), `packages/fez-git` (all four surfaces plus
two binaries), `packages/fez-score-studio` (personas only, no code).

Start with [the dev loop](/docs/extension-api/dev-loop): `fez create`,
`fez link`, publish.
