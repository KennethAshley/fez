# Dolt: fit for Fez

Reviewed 2026-09-12 using official Dolt documentation and Fez source. Source inspection only; no installation, integration or runtime tests.

## Decision

Useful when Fez agents need to collaborate on **structured datasets with reviewable changes**. Keep it optional through an extension or MCP tool. Its incremental value is database branching and merging, rather than another place to store chat or memories.

## What Dolt adds

- **Versioned SQL tables and schema.** Agents can work on separate database branches, query historical revisions, inspect row/cell changes and merge accepted work. SQL server connections can target distinct branches concurrently. [Version control](https://www.dolthub.com/docs/sql-reference/version-control/), [branch isolation](https://www.dolthub.com/docs/sql-reference/version-control/branches/).
- **Structured merge semantics.** Primary keys identify rows; conflicting changes to the same cell require resolution. Independent cells can merge, but a mechanically clean merge does not establish factual correctness. Schema conflicts and constraint violations also require handling. [Conflicts](https://www.dolthub.com/docs/concepts/dolt/git/conflicts/), [merges](https://www.dolthub.com/docs/sql-reference/version-control/merges/).
- **Explicit history checkpoints.** SQL transaction `COMMIT` and a version-control `DOLT_COMMIT` are different. Saving database writes does not, by default, create a named reviewable version-control commit; the integration must choose checkpoint boundaries or configure transaction commits to create Dolt commits. [Commits](https://www.dolthub.com/docs/concepts/dolt/git/commits/), [repository explanation](https://github.com/dolthub/dolt#make-a-dolt-commit).
- **Local operation is possible.** Dolt is a standalone binary. `dolt sql` queries a local database without a server; `dolt sql-server` provides a MySQL-compatible endpoint for shared clients. Docker and hosted services are optional. It still adds a runtime and database lifecycle to Fez. [Repository](https://github.com/dolthub/dolt), [running SQL](https://www.dolthub.com/docs/sql-reference/server/).

## Fit with existing Fez

A concrete use case: two agents enrich a shared research catalog on separate branches; a reviewer examines changed fields and merges accepted records. Each record should retain source evidence. Branch history records changes, not whether a claim is true.

Fez already has signed shared facts with authorized corrections/forgetting, plus separate encrypted private engrams. Dolt would add structured querying and alternate dataset versions, not replace those trust/privacy semantics. [Memory](../../../packages/fez-memory/README.md).

The relay already persists accepted events through JSONL or SQLite and hydrates its query index in memory. Replacing that store with Dolt would not automatically expose SQL queries. Editing a signed event's body cannot preserve its original authenticated meaning; database merges must not redefine protocol state. Storage also permits compaction, so the relay is not universally an immutable full-history archive. [EventStore](../../../packages/fez-relay/src/stores.ts).

## Git caveat

Dolt now supports Git remotes, storing database data under `refs/dolt/data` by default. This is transport reuse, not ordinary source-file Git semantics. Fez's Git extension could potentially host that ref, but compatibility is untested and its default `main` protection does not cover it; explicit ref protection and internal Dolt branch policy would be needed. [Dolt remotes](https://www.dolthub.com/docs/sql-reference/version-control/remotes/#git-remotes), [Fez Git policy](../../../packages/fez-git/src/policy.ts).
