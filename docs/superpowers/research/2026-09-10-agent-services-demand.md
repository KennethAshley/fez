# Agent services demand evidence

Checked 2026-09-10. Scope: primary-source evidence for cross-provider agent cooperation and agents paying outside services. This is a demand assessment, not a market-size estimate or an endorsement of a token/subnet.

## Evidence

| Primary source | What it establishes | What it does not establish |
|---|---|---|
| [Google Cloud: developer toolkit for A2A agents](https://cloud.google.com/blog/products/ai-machine-learning/agent2agent-protocol-is-getting-an-upgrade), 2025-07-31 | Names Tyson Foods and Gordon Food Service building collaborative agents that exchange product data and sales leads across businesses. Also describes partner agents available through an agent marketplace. | No reported task volume, payment volume, savings, retention, or proof of autonomous hiring between unknown counterparties. A named collaboration is stronger than a demo, but the wording does not quantify production results. |
| [Linux Foundation: A2A first-year adoption](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year), 2026-04-09 | Reports production deployments in several industries and integrations in major cloud platforms. Supports the existence of a cross-platform coordination problem. | Supporting organizations, repository stars, and cloud availability are supply/adoption signals, not counts of paying buyers. No repeat-purchase economics are provided. |
| [Stripe: introducing Machine Payments Protocol](https://stripe.com/blog/machine-payments-protocol), 2026-03-18 | Names Browserbase selling browser sessions to agents, Parallel Web Systems enabling payment per API call, and PostalForm enabling paid physical-mail delivery. The article explicitly characterizes direct agent-service payments as emerging and provides no quantified repeat-buyer evidence. |

## Assessment

There is credible evidence of need for agents to work across company and platform boundaries, and concrete commercial services are exposing machine-payment interfaces. This supports Fez's capability-exchange direction. It does not demonstrate demand for Fez specifically, a universal agent marketplace, a reputation subscription, or a subnet.

The strongest near-term customer proposition is a useful outcome delivered by agents operated by different providers, with less integration and payment friction. Reputation is valuable if it helps choose a provider or avoid failure. Wallets and protocols enable that transaction; they do not create the buyer's need.

None of these five official sources publishes enough repeat-buyer, unsubsidized spending, or unit-economics data to conclude that a broad independent-agent hiring market is established. This is a limit of the evidence reviewed, not proof that no such customers exist. Aggregate wallet/transaction counts were deliberately excluded: they do not identify paying customers, completed useful jobs, unique owners, or whether activity was sponsored, self-dealing, or a test.

For Fez, seek a small set of external users with one recurring job and external specialist providers. Count accepted paid jobs, repeat customers, manual rescue, and provider payouts. That tests commercial demand for the exchange directly; it does not require proving that coordination beats a single generalist model.

## Fez and subnet assessment

Recommendation for discussion, not a newly approved implementation plan: keep the communication/completion foundation, and prioritize a narrow demand pilot before broad capability rankings or subnet registration. The strongest case is an independently operated specialist bringing custom tools, data, permissions, or expertise that the requesting agent otherwise lacks. The existing speech demo establishes signed delivery and requester acceptance; it does not establish that customers prefer Fez to calling a speech API themselves.

The components have distinct jobs. Fez handles identity, communication and work exchange. Reputation summarizes evidence about specialists in particular task contexts. Payments settle authorized work. A coordination subnet could fund competing policies for specialist selection, handoff preparation, verification, recovery and final delivery. Miners would supply those policies; validators would evaluate results independently. Bittensor's own description assigns the incentive mechanism to subnet owners, work to miners, and scoring to validators; it does not supply Fez's quality rubric automatically. [Official network documentation](https://www.bittensor.com/docs/concepts/network)

Current chits are signed requester judgments. Signatures establish authorship, not honest grading or resistance to collusion. Using those records as the sole basis for emissions would create a feedback loop that controlled agents can manufacture. Independent task checks and trustworthy attribution are separate work. Consented, outcome-labelled traces may later support training; conversation volume alone establishes neither training quality nor a buyer for the dataset.

Competition is material: A2A addresses interoperability, machine-payment protocols address service purchases, and the draft [ERC-8004](https://eips.ethereum.org/EIPS/eip-8004) explicitly covers agent identity, reputation and validation. This supports the relevance of the problem while weakening any claim that combining those features is sufficient differentiation. Evaluate compatibility with existing agent ecosystems when actual prospective users identify integration barriers; no bridge is being implemented by this assessment.

Treat emissions as uncertain protocol funding, separately from customer revenue. The earlier $2,000/day remains a scenario, not an observed or guaranteed owner budget; current emissions depend on the protocol's allocation and distribution rules. [Official emissions documentation](https://www.bittensor.com/docs/concepts/emissions)

Suggested two-week pilot: three independent prospective buyers, one recurring job category, two independently operated specialist providers, and roughly ten real jobs. Agree on deliverables and payment before work; distinguish customer-funded jobs from sponsored ones. Measure accepted outcomes, repeat purchases, human rescue, delivery cost and the retained service fee. This is an early decision aid, not statistical proof of a large market. Find one buyer's current workflow before adding broad scoring machinery. No outreach, spending, mainnet payment, subnet registration, or production change was performed for this assessment.
