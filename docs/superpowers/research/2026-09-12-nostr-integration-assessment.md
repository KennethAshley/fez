# Nostr integration: architecture assessment

Reviewed 2026-09-12 against Fez source, installed `nostr-tools` 2.24.1, and current primary NIPs. This is a bounded architecture review, not a full security audit. The initial review ran one offline DM identity probe with disposable keys and changed no production code. The authorized implementation follow-up is recorded below.

## Judgment

Nostr fits Fez's central idea well: independently keyed agents exchange authenticated events, while clients enforce application rules. Keep that architecture. The next work should tighten identity validation and trust bootstrap, then make portability and delivery guarantees precise.

## Findings and priorities

1. **Strong foundation: authority stays with signed actors.** Owner-signed attestations establish agent relationships; the shared author gate defaults closed and distinguishes owner, sibling and explicit allowlist authority. It also applies where relay membership cannot, such as DMs or third-party relays. This uses Nostr's signed-event identity for a substantive purpose rather than merely replacing a chat transport. [Author gate](../../../src/identity/author-gate.ts), [attestation registry](../../../src/protocol/kinds.ts), [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md).

2. **Confirmed TypeScript DM sender-binding failure — fixed in the follow-up.** At review time, `unwrapDm` delegated to `nip59.unwrapEvent` and trusted the resulting rumor's `pubkey`. The installed JavaScript helper decrypts the wrap and seal, without checking the seal signature or comparing seal and rumor authors. An offline probe made a valid attacker-signed seal containing a rumor claiming an unrelated owner's public key, inside a valid outer gift wrap. Fez decoded it as that owner and its pure owner-only author gate admitted it. The standing agent routes decoded DMs through that gate; the live runtime was not invoked by the probe. NIP-17 explicitly requires the seal/rumor author comparison. The shared TypeScript decoder now validates this boundary; Rust already rejected the mismatch (verification below). [Fez unwrap](../../../src/protocol/dm.ts), `nostr-tools@2.24.1/lib/esm/nip59.js` (installed dependency), [agent consumer](../../../packages/fez-acp/src/agent.ts), [NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md).

3. **Pin workspace identity at join.** `openWorkspace` accepts the current primary relay's NIP-11 `pubkey` as owner; the state assignment is direct and saved workspace metadata does not pin that owner. NIP-11 defines this optional HTTP field as an administrative contact, not a signed workspace ownership certificate. Fez therefore trusts the selected relay endpoint for owner discovery. That is a legitimate bootstrap choice, but it limits claims that the relay is only storage. Recommend a trusted owner key in the invite/join record and explicit key rotation. This is not a claim that arbitrary relay events can forge owner signatures. [Client bootstrap](../../../packages/fez-client/src/index.ts), [workspace state](../../../packages/fez-client/src/workspace-state.ts), [NIP-11](https://github.com/nostr-protocol/nips/blob/master/11.md).

4. **Separate reconnect from durable replication.** The common transport fans out, accepts publication when any relay accepts, unions reads by event ID, and repairs each relay's subscriptions. Those are useful resilience features. Reissuing subscriptions does not itself copy an event from the relay that accepted it to a mirror that was offline. Describe acceptance and replication separately; add durable repair only where the product promises surviving loss of the sole accepting relay. [Transport](../../../src/protocol/relay.ts).

5. **Publish a precise Fez compatibility profile.** Fez's 40xxx/47xxx meanings are application-specific; they are outside NIP-01's replaceable/addressable ranges and its expressly listed regular ranges. Fez stores them and derives current state in clients, but arbitrary relays need verified storage/filter behavior. Likewise, inspected DM sends use configured workspace relays rather than NIP-17 recipient relay-list discovery. Specify these choices, privacy limits and required capabilities. NIP-42 access control is distinct from encryption, and NIP-44 does not provide forward secrecy. [Kinds](../../../src/protocol/kinds.ts), [relay storage semantics](../../../packages/fez-relay/src/relay.ts), [DM publishing](../../../src/protocol/client.ts), [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md), [NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md), [NIP-42](https://github.com/nostr-protocol/nips/blob/master/42.md), [NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md).

## Offline verification

The original probe (`/private/tmp/fez-nostr-dm-identity-probe.mjs`, local temporary evidence) asserted valid outer/seal signatures, different seal/rumor authors, acceptance of the claimed sender, and admission by the owner-only author gate. It reproduced twice (inline and saved script). Its assertions describe the pre-fix defect and intentionally fail after the fix; maintained rejection tests now live in `packages/fez-evals/tests/dm.test.ts`. The probe does not establish exploitation against a deployed service.

## Implementation follow-up

`unwrapGiftWrap` now verifies the outer event, seal kind and signature, rumor shape, and equality of seal and rumor authors before returning decrypted content. Both the headless decoder and desktop local signer use it; no dependency was added. Ten tests cover authenticated controls and rejection of forged authors, invalid seal signatures, wrong seal kinds, and invalid outer signatures on both TypeScript paths. Eight rejection checks failed before the fix; the DM and author-gate suites then passed all 45 tests.

An independent offline Rust probe (`/private/tmp/fez-nostr-rust-probe/main.rs`, local temporary evidence) against the cached `nostr` 0.44.8 library confirmed that the production Rust helper accepts valid messages and rejects mismatched authors, invalid seal signatures, and the wrong decryption key. No Rust edit was needed for sender authentication. This does not establish full NIP-17 conformance: its direct helper still leaves outer event verification to its caller and does not validate seal kind, supplied rumor IDs, or recipient tags.

The full build (core plus 49 packages), root `npx tsc --noEmit`, and independent scoped code review passed. The full eval gate did not produce one clean run in the concurrently changing checkout: the first unrestricted run passed 2,253 tests with one channel work-recovery timeout; that case passed separately and in the next full run. The second full run passed 2,238 tests, with two channel-completion failures and a Git workspace setup failure caused by port 7896 already being occupied. Both affected suites then passed together on retry (50 tests). These channel and Git failures do not exercise the changed DM decoder. The DM and author-gate checks stayed green; the retries do not establish a clean full-suite run. Logs: first full run (`/private/tmp/fez-dm-fix-evals-unsandboxed.log`, local temporary evidence), second full run (`/private/tmp/fez-dm-fix-evals-final.log`, local temporary evidence), final retries (`/private/tmp/fez-dm-fix-final-rechecks.log`, local temporary evidence).
