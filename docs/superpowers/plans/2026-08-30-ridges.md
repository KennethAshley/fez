# @fezchat/ridges Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the first paid-service extension — `/ridges <issue-url>` pays the Ridges subnet through the wallet's x402 rail and tracks the resulting PR, with the approved bounty-rail pane.

**Architecture:** One new package `packages/fez-ridges` (headless tool/command/poller + mount-model gui + mirrored job store) plus a small exported surface on `packages/fez-wallet` (`x402FetchRaw` structured outcome + `makeX402Deps`). All money logic stays in the wallet; ridges is service logic only.

**Tech Stack:** TypeScript, vitest (root runner), `@fezchat/wallet` via `file:../fez-wallet`, `@fezchat/extension-api` types, React + CSS module for the gui (built by `fez pack`), public GitHub REST for PR tracking.

**Spec:** `docs/superpowers/specs/2026-08-30-ridges-design.md` — grounded facts (live probe + docs), the job record, flows, and the approved visual mock (`ridges-mock.html` in the session scratchpad; its classes/copy are the visual spec).

## Global Constraints

- **No keys, no cap logic, no consent logic in fez-ridges.** Every spend goes through the wallet's `x402FetchRaw`; if a task seems to need money logic here, the plan is wrong — stop and rule.
- **The wallet's existing test surface (291+ tests) stays untouched and green.** Task 1 refactors `x402Fetch` internals; its string-tool behavior must be byte-identical (existing tests unmodified are the gate).
- **Header-version risk (spec §grounded):** Ridges documents x402 v1 names (`X-PAYMENT`/`X-PAYMENT-RESPONSE`); our SDK spoke v2 in tests. Task 1 MUST verify in `@x402` SDK source how the request-header name follows the offer's `x402Version`, and make settlement parsing tolerate both `PAYMENT-RESPONSE` and `X-PAYMENT-RESPONSE`. Record findings in the report.
- **STORAGE_NAME = the installed package name (`fez-ridges`)** — the wallet's rename bug is the precedent; a mismatched mirror name is invisible-to-the-panel data.
- Issue URLs validated to `https://github.com/<owner>/<repo>/issues/<n>` BEFORE any network. The 404 app-not-installed body's `detail` is surfaced verbatim (it carries the install link).
- Ambiguous payment surfaces the wallet's do-not-retry wording PLUS "contact Ridges support with the tx hash" (their documented recovery).
- GUI: mount model (own React, `createRoot`, disposer), CSS module (no hex — `var(--…)` tokens only), classes/copy per the approved mock; reduced-motion honored.
- Manifest permissions exactly: `network:product.ridges.ai`, `network:api.github.com`, `read:channels`, `publish`, `ui`.
- TDD; tests in `packages/fez-ridges/tests/` (+ wallet's in place); no live network in tests. Money path ⇒ final whole-branch review on a **different model** than the controller/implementers.

**Files:** Modify `packages/fez-wallet/src/tools.ts` (extract `x402FetchRaw`; `x402Fetch` becomes its formatter), `packages/fez-wallet/src/mcp.ts` (export `makeX402Deps`), `packages/fez-wallet/package.json` (exports map if present); Test: `packages/fez-wallet/tests/x402-raw.test.ts` (new only — existing tests UNMODIFIED).

**Interfaces (produces, consumed by Task 3):**
```ts
type X402Outcome =
  | { kind: "response"; status: number; bodyText: string }                          // non-402 passthrough (e.g. the 404 guard)
  | { kind: "paid"; status: number; bodyText: string; txHash?: string; usd: number }
  | { kind: "refused"; message: string }                                            // never-paid: policy/consent/no-offer
  | { kind: "ambiguous"; message: string; usd: number; txHash?: string };           // may have settled
export function x402FetchRaw(deps: X402ToolDeps, args: { url; method?; body?; maxUsd }): Promise<X402Outcome>
export function makeX402Deps(persona: string): X402ToolDeps   // exported from mcp.ts's existing builder
```

- [ ] Step 1: failing tests — `x402FetchRaw` returns each `kind` for the scenarios the existing tool tests already stage (reuse their mocks): non-402 → `response` with body; refusal → `refused` (zero writes, as before); paid via the in-test 402 server → `paid` with usd + txHash; second-402 → `ambiguous`. Plus: settlement parse accepts a server answering with `X-PAYMENT-RESPONSE` (v1 name) — this test fails today.
- [ ] Step 2: RED → refactor: move the flow body into `x402FetchRaw` returning the union; `x402Fetch` maps outcomes to the EXACT current strings (each existing string built from outcome fields). Widen settlement parsing to try both header names (in the wallet's parse helper). Verify in `node_modules/@x402/*` source how request-header naming follows the offer's `x402Version`; write findings into the report.

## Task 4: the PR poller

**Files:** Create `src/poller.ts`; Modify `src/headless.ts` (registerScheduledTask, 90s); Test `tests/poller.test.ts`.

**Interfaces:** `pollOnce(deps: { dir; fetchImpl; now }): Promise<void>` — reads open jobs (`working`/`pr-open`), one GitHub pulls request per distinct repo per tick with stored ETags (`If-None-Match`; 304 → skip), matches via `matchPr`, records `prUrl/prNumber` permanently on first match, transitions per PR state (`pr-open` → `merged` when `merged_at` set, `closed` when closed unmerged), mirrors on change. 403 with `x-ratelimit-remaining: 0` → store the reset time, skip that repo until past it. Repo 404 → job note "repo unreadable — private? token support later", stop polling that repo this session.
